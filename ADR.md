# Architecture Decision Records

## 1. Choose Flask and built-in sqlite3 over FastAPI and Django
Date: 2026-10-05
Status: Superseded by [7]
Context: This assignment needs a small web app that runs as one process and gets containerised later. It has two domains and a handful of pages, and the brief requires SQLite for storage.
Decision: I chose Python with Flask for the web pages and Python's built-in sqlite3 so I can write the SQL queries myself. The app is served by waitress, which app.py starts, so "python app.py" is the only command needed.
Alternatives considered: I considered Django because I used it last semester in my Database class, but it comes with features this app does not need, such as the admin panel, and it needs a manual "python manage.py migrate" step before its tables exist, which conflicts with the brief's rule of no manual setup at startup. I also considered FastAPI, but it is designed for JSON APIs while this app serves HTML pages, and it has concepts I would have had to learn first. I did not add an ORM like SQLAlchemy because it is an extra package and it generates the SQL for me, so I could not explain those queries myself.
Consequences: I have to write myself what Django would have given me: the SQL queries, creating the tables at startup and form validation, and there is no ready-made login if I ever need one. But in return, the app depends on only 4 direct packages.

## 2. Keep catalogue and show builder as separate packages
Date: 2026-10-06
Status: Decided
Context: The brief requires two separate feature areas, the catalogue and the show builder, which could later become independent services. Because of that, they should not be too tightly connected.
Decision: The code will be split into two folders, catalogue/ and shows/. The show builder will only store a song_id and will ask the catalogue for the full song details when needed.
Alternatives considered: A simpler option was to put everything in one folder, or organise it only by type, such as keeping all database code together and all pages together. I rejected that because it would mix the two domains and make them harder to separate later.
Consequences: The cost is that the structure is slightly more complex and some communication between the two parts is needed. The benefit is that the code is cleaner and each domain can be changed or separated more easily later.

## 3. Setlist items reference songs by ID only
Date: 2026-10-08
Status: Decided
Context: The catalogue and show builder are separate domains, so a decision is needed about how setlists refer to songs without tightly coupling both parts.
Decision: setlist_items stores only the song_id, not the full song data. When the show builder needs the details, it asks the catalogue through two read-only functions, get_songs_by_ids() and list_active_songs().
Alternatives considered: The normal approach would be a foreign key from song_id to songs, or a SQL JOIN between the show and catalogue tables. It would make a future split into separate services harder because the songs table would then live in a different database, and a foreign key cannot point into another database.
Consequences: The cost is that the database can no longer guarantee that every song_id actually exists in songs. The benefit is that if the catalogue becomes a separate service later, the show builder can keep storing IDs and only the way it fetches song details would need to change.

## 4. Test rules and services first, keep routes thin
Date: 2026-10-10
Status: Decided
Context: The brief asked for at least 70% test coverage, so I focused on testing the parts of the program where the important decisions are made. I wanted to make sure the main rules of the app were properly checked.
Decision: I tested the six checks in shows/rules.py most thoroughly, reaching 100% coverage, and then tested the services and repositories, which are around 99-100%. I kept the routes thin because they do not contain the actual rules; they mainly call the services, run the checks, and pass the results to the pages.
Alternatives considered: I could have tested the web pages using Flask's test client as well. I did not make that the priority because the brief asks for coverage of the core business logic, and page tests would mostly check HTML and could break after visual changes even when the actual rules still work correctly.
Consequences: The downside is that the routes and app.py still have 0% coverage, so some page or routing problems might not be caught by the tests. The benefit is that the most important logic is well tested, the tests are fast, and the project now has 77% coverage of the app code, which is above the required 70%.

## 5. No login in this version
Date: 2026-10-11
Status: Decided
Context: The app is designed as a simple tool for one tribute act. The musical director and manager have different jobs, but they are still part of the same small trusted team. Because they trust each other, separate accounts and permissions are not necessary yet.
Decision: I decided not to build a login in this version.
Alternatives considered: I could have added something simple like one shared password for the whole app, or used a login library such as Flask-Login. One shared password would add very little because everyone would still use the same identity. It would not tell us who changed what, so it would not give much accountability. A full login with a library would add extra work without being necessary yet.
Consequences: Right now the app runs on a trusted machine or local network, so anyone with access to that network can view and change the catalogue and shows. A login would become necessary before deploying it somewhere like Azure where other people could access it, and that would mean adding user accounts, password handling, authentication, probably new database tables, and deciding which user can see or edit which shows and songs.
## 6. Split into a catalogue service and a shows service
Date: 2026-11-10
Status: Decided
Context: Assignment 2 asks for the app to run as separate services. ADR-2 and ADR-3 already kept the two domains apart, with the show builder reaching the catalogue only through get_songs_by_ids() and list_active_songs(), so that seam is the natural place to cut.
Decision: The code is split into services/catalogue and services/shows. Each one is its own Flask app with its own Dockerfile, requirements.txt, tests and SQLite file under DATA_DIR. The catalogue service owns the outfits and songs tables (catalogue.db) and keeps the demo seed. The shows service owns the shows and setlist_items tables (shows.db). The two seam functions became read-only JSON endpoints on the catalogue, GET /api/songs?ids=... and GET /api/songs/active, and the shows service calls them over HTTP from shows/catalogue_client.py, using the address in CATALOGUE_URL. Both services answer GET /health. docker-compose.yml starts both, with one named volume each.
Alternatives considered: I could have kept one database file and mounted it into both containers. I rejected that because both services could then read and write each other's tables, and the split would only exist in the folder names. I could also have kept the shows service importing the catalogue code, but then it could not be built or deployed on its own.
Consequences: The show page now depends on the catalogue being reachable: if it is down, the page fails, which is a TODO in catalogue_client.py. Every show page makes one or two HTTP calls instead of function calls. The links between the pages of the two services go through CATALOGUE_PUBLIC_URL and SHOWS_PUBLIC_URL, because the browser and the shows container reach the catalogue at different addresses. In return, each service has its own data, its own image and its own tests, and the shows tests use a fake catalogue instead of the real one.

## 7. One SQL Server database per service, with forward-only numbered migrations
Date: 2026-11-17
Status: Decided
Context: The brief requires one SQL Server database per service. On Azure, Container Apps removes a container when it scales to zero, and its filesystem goes with it, so a SQLite file written inside it would be gone after every idle period. Until now each service kept its own SQLite file in a Docker volume, with only demo and test data, so there was no real user data to move: the new databases could start empty, run the migrations, and seed the catalogue again. In Assignment 1 I chose not to add a foreign key on song_id (ADR-3), even though both tables were in one database and I could have. Now I can't add one even if I wanted to, because songs live in another database. So the split turned my choice into a constraint: integrity was already checked in code, and now that is the only option.
Decision: Each service has its own database (catalogue, shows) and its own login (catalogue_app, shows_app). That login only gets the permissions it needs inside its own database: read, write and create tables (db_datareader, db_datawriter, db_ddladmin), and nothing in the other one. Locally they are created automatically by db/init.sql through the db-init service in compose; on Azure they are created once during the initial setup. The schema is defined by numbered SQL files in each service's migrations/ folder, starting with 001_init.sql, applied by my own small runner (app/migrate.py). Migrations run in order when the service starts, before it begins serving requests, and applied migrations are tracked in schema_migrations. Each file and its row are written in one transaction, so if a migration fails halfway nothing is left half-applied and it is retried on the next start. They are forward-only: to fix something I add a new migration instead of editing an old one. show_date is a real DATE, because SQL Server then validates and compares dates properly instead of accepting any text. I kept SQL Server's case-insensitive collation, because names like "Red jacket" and "red jacket" should count as the same outfit, and it helps avoid duplicates. Raw SQL stays as in ADR-1; only the driver (pymssql) and the dialect (T-SQL) changed. This replaces the SQLite storage detail of ADR-6; the split itself still holds.
Alternatives considered: I could have used SQLAlchemy with Alembic. I kept raw SQL because ADR-1 already chose it, and it makes every query and migration easy for me to understand and explain at the closed-book check; my runner is short (about 50 lines) and I can explain it on paper. For only four tables, two more packages and SQL generated for me would add more complexity than benefit. I could have written a down migration for each file. I chose forward-only because undo scripts are rarely tested, so they tend to fail exactly when you need them, and they can be risky when they remove columns or data; if something is wrong, I fix it with a new migration. I could also have written a script to copy the SQLite rows into SQL Server. There was no real data to move, only demo and test data: the catalogue recreates its demo data itself, and the shows I had created while testing locally were simply dropped. A one-use copy script would have added risk for no real benefit.
Consequences: A song_id can point to a song that no longer exists, for example after the catalogue is reset. I handle that by checking the song with the catalogue when it is added; later the setlist either reports it as missing, or skips the checks if the catalogue service itself is unavailable. Recovery plan for a bad migration in production: if a migration fails, the transaction rolls it back, so the previous version can still be redeployed using its old SHA. If a migration succeeds but is wrong, the fix goes in a new migration through PR and CI. To keep rolling back the image safe, I write migrations as additive changes: add a new column with a default value instead of renaming or dropping an existing one. The old image never reads the new column, so it keeps working after the migration is applied. A rename or drop needs two steps: first add the new column and change the code, and only later remove the old one. If data is damaged, I restore the database from Azure SQL's automatic backups (point-in-time restore), which I confirmed is available on the free offer on 20 Nov: after the first backup, both databases report an earliestRestoreDate. The main downside for me as a developer is that testing is slower and needs SQL Server running, so setup is more complicated than with SQLite: the catalogue tests went from about 7 s to about 70 s. The benefit is that I now test against the same kind of database as production, each service has isolated data, and the data survives container restarts and scale-to-zero.

## 8. Serverless hosting on Azure: Container Apps that scale to zero and free-offer serverless databases
Date: 2026-11-20
Status: Decided
Context: Everything on Azure has to be pay-per-use, so the Container Apps scale to zero and the Azure SQL databases pause when nobody is using them. The professor's guide moved everything to my own Azure for Students subscription ($100 of credit) in my own resource group rg-fmedina-ieu2024, and the UI to a Storage static website instead of Static Web Apps. Azure for Students cannot charge me: when the credit runs out, the resources stop. So the real risk is not a bill but the app going offline before grading ends, and an idle system that costs nothing is what keeps it online. This makes sense for this app because the musical director and the manager only use it occasionally, before a show, so paying for always-on servers would be waste. The two halves do not go idle on the same clock. A Container App goes to 0 replicas about 5 minutes after its last request, while a database pauses after 60 minutes without connections (fixed by the free offer). After about an hour idle, both Container Apps are at 0 replicas and both databases are paused. The first request is then slow, because Azure has to start a container, the app has to connect while the database resumes, and it checks its migrations before it answers; I measured that on 22 Nov (see Consequences). I saw this during the setup on 20 Nov: both databases first answered "Database '...' is not currently available. Please retry the connection later." The setup script had to retry every 20 seconds until they woke up. At first it only waited for the catalogue database, so creating the shows user failed, and we fixed the script to wait for each database.
Decision: The two services run on Container Apps (Consumption plan), fmedina-ieu2024-catalogue and fmedina-ieu2024-shows in the environment fmedina-ieu2024-env (swedencentral). They are billed per vCPU-second, GiB-second and request, with a monthly free grant for the subscription (180,000 vCPU-seconds, 360,000 GiB-seconds, 2 million requests), so they cost nothing at 0 replicas. The two databases, fmedina-ieu2024-catalogue-db and fmedina-ieu2024-shows-db on the server fmedina-ieu2024-sql, are Azure SQL serverless on the free offer: 100,000 vCore-seconds and 32 GB free per database per month. With AutoPause, a database that uses up its allowance pauses until the 1st instead of being billed. The UI is a Storage static website (fmedinaieu2024ui) of under 1 MB, so it costs under $0.01 a month. The pipeline signs in as the managed identity fmedina-ieu2024-github with a federated credential (free, no password), logs go to Log Analytics (free up to 5 GB a month), and the images are on GHCR (free). Each Container App has min 0 and max 1 replicas. Min 0 lets the services scale down fully, so nothing runs or is billed while nobody uses the app. Max 1 is there because migrate.py runs the migrations at startup: two replicas starting together could both try to apply the same migration and race on schema_migrations. concurrency: deploy in cd.yml means two deploys can't overlap either, and max 1 also caps the cost. A cold start is covered by timeouts that fit inside each other. db.py makes 8 connection attempts with waits of 1, 2, 4, 8, 15, 15 and 15 s, about a minute, while the database resumes. If the container is not ready, Azure's ingress answers 503 "App port is not ready" after about 30 s. ui/js/api.js treats a 5xx without our error shape as no answer, says the service "is not answering. It may be starting up", and offers Try again; by the time the user tries again, the database has usually resumed. The 60 s timeout in api.js is only the backstop for a request that gets no answer at all. cd.yml polls /health for up to 5 minutes, not 1, because a first deploy can be a container start plus a database resume plus the migrations, and a 1-minute limit could fail a deploy that is actually fine. The SQL server uses the Proxy connection policy. Proxy keeps every SQL connection on port 1433 through Azure's gateway, instead of the default Redirect to ports 11000-11999, which FreeTDS (used by pymssql) may not follow reliably. The CD job reads each app's address with az containerapp show, because Azure generates it, so nothing is hardcoded in cd.yml and it stays correct if a Container App is recreated. The setup is Azure CLI commands, run once and written in order in the README.
Alternatives considered: I could have set --min-replicas 1 on both apps. That would remove the container cold start, so the musical director would never wait for a container. But the brief requires minimum replicas 0. One app at 0.25 vCPU for a 30-day month is 0.25 x 2,592,000 = 648,000 vCPU-seconds, about 1.3 million for both, against a free grant of 180,000 for the whole subscription, so both apps would be billed all month. It also wouldn't solve the bigger delay: the app opens a connection per query and never pings the database, so the database would still pause after 60 minutes. I could have used a serverless database without the free offer (15-minute pause, 2 GB, like the group project). It pauses sooner, so each wake-up is billed for less time, but every vCore-second is billed from the first one. The free offer gives 100,000 vCore-seconds per database per month, and AutoPause keeps the database at $0 when it reaches the limit. Its downside is the fixed 60-minute pause, so each wake-up costs at least 60 minutes x 0.5 vCore = 1,800 vCore-seconds, about 55 wake-ups a month, but for this project $0 matters more. I could have written the infrastructure as code with Bicep or Terraform. I used the CLI because the setup only needs to run once, every command is documented in order in the README, and I can explain each step at the check; Bicep or Terraform would be another language to learn before Sunday. The downside is that the CLI is not declarative: rebuilding everything means re-running the commands by hand, a manual change in the portal (drift) would go unnoticed, and I give up the credit the brief gives for well-understood IaC. I kept CORS in cors.py instead of the Container Apps ingress setting, because the professor's guide says CORS on the ingress breaks every POST with "Failed to fetch", and cors.py also does the Origin check against CSRF, which the ingress can't do. I used GHCR instead of Azure Container Registry, because GHCR is free and ACR has a fixed monthly fee that the brief says would need justifying.
Consequences: If the musical director comes back within 5 minutes, everything is warm and the app is instant. I measured the other two cases on 22 Nov, on the deployed system. After a coffee break (5-60 minutes; I measured about 17 minutes idle) only the container has to start, because the database is still awake, and that alone took over 30 s, not the few seconds I had expected: at 34 s the ingress answered 503 and the UI showed that the service may be starting up, with Try again; after Try again the page loaded at once. After about 2 days idle, when the container had to start and the database had to resume, the shows list appeared after about 45-50 s, with only "Loading..." on screen and no error, inside the 60 s timeout of api.js. Start times vary: the 2-day case also needed a container start but got no 503, and I don't know why. So the musical director should expect a wait of half a minute to a minute on the first visit of the day, and on some visits a "starting up" message and one click on Try again. If shows answers while the catalogue is still waking up, it only waits CATALOGUE_TIMEOUT (5 s), so the setlist loads degraded (no song details, checks skipped), and a refresh a bit later shows everything. Max 1 replica is per revision: during a deploy, the new revision starts and migrates while the old one is still serving for a moment. So the old code can run on the new schema, which is why migrations must stay additive, as ADR-7 says. For me as the developer, the Azure setup is manual (the commands in the README) instead of one command. Logs are read with az containerapp logs show instead of in my terminal. I avoid testing against Azure, because every connection wakes a database and spends part of the ~55 wake-ups a month, so most testing happens locally and in CI. The Proxy policy adds a little latency to every query, because each one goes through Azure's gateway. At 100x traffic I would make four changes. First, allow more than one replica, but before that move the migrations out of app startup (a CD step that runs them once before deploying, or a lock), so replicas cannot race on schema_migrations. Second, stop auto-pausing the database, since the free offer would run out within days, and move to a paid tier. Third, cache GET /api/songs/active in shows for about 30-60 seconds, because the catalogue changes rarely (the musical director edits it now and then, while the manager opens overviews all the time, and every overview calls it). The risk of a stale cache is that a song retired a minute ago still shows as addable in the picker. That is acceptable, because adding a song still checks with the catalogue that it exists and is active, so the add is refused with "That song is retired." I would not cache GET /api/songs?ids=, since the overview should show the current song details. Fourth, the logs: one line per request from request_log.py would go past the 5 GB a month free in Log Analytics, so I would stop logging the /health calls from probes, sample the successful requests while keeping every error, and shorten the retention before accepting to pay.

## 9. CI gates on lint, tests with 70% coverage, the system description and a cross-seam test on the compose stack
Date: 2026-11-19
Status: Decided
Context: Every change reaches main through a pull request, and from Friday every merge to main is deployed to Azure, so CI is the last check before users see a change. The brief requires lint, tests with at least 70% coverage per service, validation of system.yaml and each openapi.yaml, image builds, and at least one test across the seam. Tests must never use Azure SQL.
Decision: CI (.github/workflows/ci.yml) runs on every push and pull request. The test job (one per service) runs ruff, then the tests against a SQL Server container with a 70% coverage gate over all of app/. The validate job checks system.yaml against the professor's system.schema.json and each openapi.yaml against the OpenAPI specification, and checks that the files copied into both services are still identical. The integration job brings up the whole compose stack and tests shows calling the real catalogue, including with the catalogue stopped. The images job has needs: [test, validate, integration], so if any check fails no image is published, and from Friday nothing is deployed. Each gate has a real reason in this project: ruff found an unused import of format_duration in shows/service.py; validate caught an unquoted comma in system.yaml that split a description into a stray field, which only additionalProperties: false noticed; and the drift tests (test_openapi.py, test_system_yaml.py) fail when an endpoint is not documented or an env var in config.py is missing from system.yaml. The coverage gate has not failed yet, as both services are at about 99%, but it measures all of app/, so db, migration, health and CORS code cannot be added untested. CI never uses Azure SQL: every connection wakes the database and uses up its free monthly allowance, which CI on every push could exhaust, leaving the deployed app without a database (or billing) late in the month; and the tests drop and empty tables, so they must never touch real data. A disposable SQL Server container speaks the same T-SQL and uses the same per-service logins from db/init.sql, for free. The cross-seam test is tests/integration/test_seam.py, at the repository root because it tests both services together, run by the integration job against the stack from docker compose up -d --build. It first waits until both /health endpoints return 200, creates a show and adds a real song from the catalogue. The first test checks that the overview's song is exactly what the catalogue answers at GET /api/songs?ids=, and that the running time is that song's duration, so the checks ran on real data. The second test runs docker compose stop catalogue and checks that the overview still returns 200 within 15 s (not hung), that catalogue_available is false, that song and problems are null (the checks were skipped, not "no problems"), that adding another song returns 503 and saves nothing, and that shows' own /health stays 200. At the end it starts the catalogue again and deletes its show, so it leaves nothing behind.
Alternatives considered: I could have started a real catalogue process from a shows test. That would not test the actual Docker images or the compose networking between the services, so a wrong Dockerfile or a bad CATALOGUE_URL=http://catalogue:8000 in compose could still pass. I could have replaced the catalogue with a stub. A stub only returns the response shape we expect, so it can hide real compatibility problems: if someone renamed duration_seconds in the catalogue's response, the stub would still send the old name and the test would pass while the real app broke. With the real catalogue, the test fails if the actual API changes in a way that breaks shows. For the code both services need, I could have shared it, as a common/ package both Dockerfiles copy or a small library both install. I kept separate copies because each service should be able to build, test and deploy independently. Each Dockerfile's build context is its own folder (services/catalogue, services/shows), so a common/ package outside it could not even be copied into the image without changing both Dockerfiles; and a shared package would couple them: a change to db.py made for shows would rebuild and redeploy the catalogue too, and could break it.
Consequences: Some things are deliberately not tested. The /health 2 s limit: when sqlserver is stopped locally, its name disappears from Docker's DNS and each failed lookup takes about 3 s, twice, so the 503 took 6-12 s; login_timeout does not cover that lookup. A hard 2 s deadline would need a thread with a timeout, extra complexity I could not easily explain, so I accepted it: Docker's HEALTHCHECK has its own --timeout and still marks the container unhealthy, and on Azure the server name always resolves (a paused database answers 40613 at once), so the 2 s limit should hold there; I will confirm it on Friday. A slow catalogue: test_every_call_uses_the_timeout_from_config checks that CATALOGUE_TIMEOUT (5 s) is passed to every catalogue request, but nothing simulates a catalogue that accepts the connection and then waits more than 5 s; that would need a fake service that does exactly that, and a check that shows degrades in about 5 s instead of hanging. The UI's JavaScript: the risk is a broken button or page that CI would not notice; it is covered by my manual browser click-through (including with the catalogue stopped), and every API it calls is tested automatically. Real Azure: the risk is something that only fails in the cloud (cold starts, the paused database, CORS with the real UI origin). From Friday the pipeline checks /health after deploying and that its version is the new SHA, which proves the new version is running, and it sends one request with Origin set to the storage website's origin and checks the Access-Control-Allow-Origin header, so CORS on Azure is tested too. The services share no code, so some code is copied. Byte-identical in both services: app/db.py, app/migrate.py, app/request_log.py, app/cors.py, app/health.py and tests/test_system_yaml.py. Nearly the same: the error_as_json handler in each main.py, read_form and errors_response in each api.py, the table cleaning in each tests/conftest.py, tests/test_health.py, the route helpers in tests/test_openapi.py, and ruff.toml. Still duplicated from Assignment 1: format_duration (catalogue service.py, shows rules.py) and parse_whole_number (catalogue service.py, shows service.py). Copied on purpose: the seam schemas CatalogueSong and CatalogueActiveSong in services/shows/openapi.yaml, kept equal to the catalogue's by test_openapi.py. The cost is that the same bug, for example in db.py's retry logic, has to be fixed twice, and the copies could slowly drift apart. This ADR and the README list them, and for the byte-identical ones the validate job runs cmp and fails if any byte differs; when I added it, it found that the first docstring line of db.py had differed since 17 Nov. The nearly-same copies are only checked by review. If the shared code became much bigger, changed often, or I had more services, copying would stop being worth it: I would move it into a small versioned package and let each service depend on a pinned version.

## 10. Not built: a message broker to tell shows when a song is retired
Date: 2026-11-22
Status: Decided
Context: When the musical director retires a song in the catalogue, the shows service is not told. It only finds out when someone opens a show that uses the song: show_overview calls the catalogue with GET /api/songs?ids=, and check_retired_and_repeated_songs flags the retired song on the show page. Until someone opens that show, nobody knows. This matters more since migration 002: a show can now be confirmed, so a booked gig can contain a retired song, which is a real problem, and the manager only sees it by happening to open that show. The shows list does not run the checks, so it gives no warning either.
Decision: I deliberately did not build a message broker. The broker version would work like this: the catalogue publishes a "song retired" event with the song id to a broker (Azure Service Bus), and shows listens, finds the setlist items with that song_id in confirmed shows, and flags them for the manager. Instead, the seam stays as it is: the catalogue never calls shows, and shows asks the catalogue for the current song details every time an overview is loaded, so a show page is never out of date, it just has to be opened.
Alternatives considered: Service Bus itself. A topic, so that more than one service could receive the same event, needs the Standard tier, which has a fixed hourly base charge, against the brief's pay-per-use rule. Basic is billed per operation but has only queues, so one listener per message. The listener would not have to run all the time, since a Container App can scale from 0 on a queue's length, but every event after an idle period would then start the shows container, and the system would gain another resource, a connection string to keep as a secret, and one more place where the two services can disagree. Above all, §1c lists message brokers as out of scope. A cheaper way to get most of the benefit, with no broker and no extra resource: when the musical director clicks Retire, the UI (which already calls both services) asks shows which confirmed shows use that song and warns before retiring. That needs one new shows endpoint (the confirmed shows that contain a song_id), and it is a client-side cross-seam flow, like the rest of the UI. Or the shows list could run the retired check and show a warning badge on each confirmed show; it should collect the song ids of all confirmed shows and make one GET /api/songs?ids= call, not one per show, so the list stays a single call to the catalogue and still degrades like the overview when the catalogue is down. I built neither, because the brief asks for no new features, and the musical director and the manager can open their next few confirmed shows before each gig.
Consequences: A confirmed show can contain a retired song for days without anyone knowing, until someone opens it; the show page then says "Position N: "TITLE" is retired." and the setlist can still be fixed before the gig. The benefit is that the catalogue does not depend on shows at all (it never calls it), there is no extra Azure resource to pay for or secure, and nothing runs while the app is idle. A broker would be worth building with many confirmed shows a month or several people editing the catalogue, when the manager must be told right away (for example by email) without opening the app, or when more services need the same event. Before that point, the warning before retiring is the first step, since it costs one endpoint and no infrastructure.
